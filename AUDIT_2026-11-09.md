## 2. Verified findings — still open

### V3 — Admin-tier *page* guard is not trial/plan-gated — Medium
- `lib/auth/guard.ts` `requireAdminTier()` (≈line 88–115): checks role and module
  access but never `isTrialExpired(user)`. The API guards
  (`requireApiPermission`, `requireApiDoctorOnly`) and server-action scope
  (`lib/auth/action-scope.ts:74`) *are* gated, so data endpoints refuse an expired
  owner while the dashboard pages still render. Inconsistent expiry enforcement.
- **Fix:** add the `isTrialExpired` check to `requireAdminTier` (redirect to
  `/trial-expired`, mirroring the doctor shell).
- **Verification method:** render `/admin` as an expired owner in staging.

### V4 (partial) — `sos_requests` coordinates remain varchar — Medium/High
- `lib/db/schema.ts:65-66` (`sosRequests.latitude/longitude` varchar) while
  `sosCases` was migrated to `DECIMAL(10,7)` (schema.ts:1655, 1725-1726). The
  dispatch discovery scan reads `sosRequests`, so distance math still relies on
  implicit string→number coercion and range predicates stay unindexable.
- **Fix:** additive migration `ALTER TABLE sos_requests MODIFY latitude
  DECIMAL(10,7), MODIFY longitude DECIMAL(10,7)` + backfill validation; then a
  bounding-box prefilter in `lib/dispatch/geo.ts`.
- **Verification:** `EXPLAIN` the discovery query before/after.

### V5 (partial) — Vendor upload: TTL yes, rate limit no — Medium
- `app/vendor/upload-test/[token]/actions.ts` now enforces the 7-day token TTL
  (`token-ttl.ts`, fail-closed) but still has **no rate limiter** on the
  unauthenticated upload endpoint (grep for limiter imports: 0 hits). An attacker
  can still flood uploads within the TTL window.
- **Fix:** IP-keyed limiter (e.g. 5 uploads/hour/IP) in the action before I/O.

### P2 (partial) — Growth dashboards bucket in JS over unbounded scans — Medium
- `lib/queries/super-admin.ts:51-90` (`getDoctorGrowth`, `getPatientGrowth`):
  `SELECT created_at FROM users WHERE role = …` with **no LIMIT and no SQL
  aggregation**, then buckets every row in JS. Cost grows linearly with total
  users on every super-admin dashboard load (React `cache()` is per-request only).
- **Fix:** `DATE_FORMAT(created_at, '%Y-%m')` GROUP BY aggregation, or a monthly
  counter table; bound to the same N-month window in SQL.

### V9/V12 (carried) — CSRF + throttle are per-route, not in the guards — Medium
- Still opt-in per route. The durable fix from the prior plan (move both into
  `requireApiRole`/`requireWriteScope` with an explicit opt-out list) remains open.

### R6 — `REDIS_URL` is documentation-only — Medium (maintainability trap)
- Single-instance remains a hard constraint (in-memory rate limiter + SOS hub).
  Any second PM2 worker silently breaks emergency dispatch correctness. Keep the
  README constraint; implement the Redis backend before any scale-out.

## 3. Verified findings — fixed in this session

### V1 — Unauthenticated cross-tenant PHI read via exported server action — CRITICAL → FIXED
- **Evidence (pre-fix):** `app/admin/consultations/[appointmentId]/actions.ts:30`
  exported `getConsultationRecordForAdmin(appointmentId, doctorIds)` from a
  `"use server"` module with **no auth check inside** and `doctorIds` accepted from
  the caller. Every export of a `"use server"` file is a directly invocable RPC
  endpoint whose arguments are attacker-controlled — any unauthenticated party
  could pass `appointmentId` + an arbitrary `doctorIds` list (e.g. `[1]`) and read
  consultation notes, diagnosis, medications, patient name and phone across **all
  tenants**. The page caller derived scope correctly, but that protects only the
  rendered page, not the action endpoint.
- **Fix applied:** the action now derives scope internally via
  `getBusinessScope()` (which redirects unauthenticated / out-of-tier callers
  before any query) and the caller-supplied parameter was removed; the single
  caller (`page.tsx`) was updated; the scope-empty case returns `null` → `notFound()`,
  keeping a miss indistinguishable from a genuine miss (no enumeration oracle).
- **Verified:** tsc clean, 180/180 tests, build succeeds. **Staging check still
  recommended:** POST the action id without a session cookie and confirm a redirect.

### V2 — Unpatched critical framework advisories — CRITICAL → FIXED
- **Evidence (pre-fix):** `npm audit --omit=dev` on next 16.3.0 reported 4
  vulnerabilities (1 critical, 3 high), including **unauthenticated RCE on
  Windows-hosted servers** (GHSA-p293-qw3h-jr36), **RCE in Image Optimization**
  via AVIF/SVG (GHSA-2xp9-vwfh-vxw4, GHSA-2464-fhr4-w9xw), **RCE in next/og
  ImageResponse** (GHSA-vcvr-r3jv-pc5j), **RCE in `use cache` typed arrays**
  (GHSA-673q-mjm6-r5xr), **SSRF in Image Optimization** (GHSA-cjq9-62q9-8jv4),
  **DoS via Server Actions** (GHSA-p3m5-59mp-jv5r), cache-poisoning of SSG/ISR
  pages, and zod <4.6.6 memory exhaustion (GHSA-mrhx-c7xc-m3w5).
- **Fix applied:** `next` 16.3.0 → **16.4.5**, `zod` → **4.6.7**, `npm audit fix`
  for the transitive `source-map-js` advisory. Production audit now reports
  **0 vulnerabilities**. (The `sharp` librsvg advisory resolved out with the
  dependency refresh.)
- **Verified:** full test suite, typecheck, all three guard scripts, and a
  production build all pass on 16.4.5.

### V6 — Production CSP blocked Razorpay Checkout — High → FIXED
- **Evidence (pre-fix):** `proxy.ts` `buildCsp()` shipped `frame-src 'self'` and
  production `connect-src 'self'`. `components/packages/package-checkout-button.tsx`
  injects `https://checkout.razorpay.com/v1/checkout.js` (permitted only via
  `'strict-dynamic'` script inheritance) and opens a cross-origin payment iframe
  that posts to `api.razorpay.com` — both blocked in production. Owner-tier
  purchases could not complete.
- **Fix applied:** production CSP now allows `frame-src … https://api.razorpay.com
  https://checkout.razorpay.com` and `connect-src … https://api.razorpay.com
  https://lumberjack.razorpay.com` (dev unchanged, still `'self'`-only).
- **Verified:** production build emits the new CSP; **runtime checkout
  click-through should be confirmed once in staging** (build-level verification
  only — no live payment was executed).

### Portability note — `npm run build` fails on Windows
- `package.json` `build` script uses a POSIX env prefix (`NODE_ENV=production
  next build`), which cmd.exe cannot run. Fine on the Linux deploy box; breaks
  Windows dev. Low priority: `cross-env` or a plain `next build` (Next sets
  production mode itself).

## 5b. Session 3 — V9/V12: CSRF + throttle moved into the shared guards

### V9 + V12 — inconsistent CSRF reach and missing throttles on guard-protected routes — MEDIUM → FIXED
- **Evidence (pre-fix):** the mobile namespace wrapped its actors with
  `withThrottle` and `csrfGuard`, but **72 non-mobile route files** called
  `requireApiRole` / `requireApiPermission` / `requireApiDoctorOnly` directly —
  no per-user budget, and a foreign-`Origin` state-changing POST was only
  refused where the route remembered to call `rejectForeignOrigin` itself.
- **Fix applied:** both checks now run INSIDE `requireApiRole`
  (`lib/auth/guard.ts`), which the other two guards delegate to — so every
  guard-protected route gets them with zero call-site changes:
  - **CSRF:** `checkSameOriginHeaders(await headers())` — new Headers-based
    variant in `lib/security/csrf.ts` (the Request-based API is unchanged and
    now delegates to it). Foreign Origin → 403; absent Origin (native app,
    curl, webhooks) passes, per the module's documented threat model.
  - **Throttle:** `authRateLimit.apiGuard(user.id)` — new entry keyed on the
    resolved user id (identity, not IP), 300/min default, env
    `RATE_LIMIT_API_GUARD` / `RATE_LIMIT_API_GUARD_WINDOW_MINUTES`. Mobile
    routes keep their own identical-budget bucket; two independent generous
    budgets bind at the same effective rate, neither halves the other.
  - **Ordering preserved:** 401 (no session) → 403 (wrong role) → 403
    (foreign Origin) → 429 (budget). An unauthenticated caller still gets its
    401, never a 429/403 that reveals the endpoint exists — the same ordering
    rationale the mobile helpers document.
- **Tests added:** 2 cases in `lib/security/__tests__/csrf.test.ts` — the
  Headers variant agrees with the Request variant on every case class, and
  allows absent/own-host Origin while refusing foreign.
- **Verified:** tsc clean · **182/182 tests** (was 180) · build succeeds ·
  live smoke test against `next start`: guarded route unauthenticated → 401
  (correct ordering), with foreign Origin and no session → 401 (auth precedes
  origin, as designed), `/api/health` → 200, `/` → 200.
- **Not verified by execution:** the authenticated foreign-Origin → 403 path
  and the 429 path need a real session — staging check (send a same-site POST
  with a tampered Origin header using a live session; expect 403).

## 5c. Session 4 — P4/P6: bounded-reads sweep + the finance-trend fix

### P2 (carried HIGH) — `getPracticeFinanceTrend` pulled the whole ledger — FIXED
- **Evidence (pre-fix):** `lib/queries/doctor.ts` selected `date/type/amount` of
  EVERY approved transaction ever (no window, no LIMIT) and bucketed six months
  in JS — the prior audit's remediation item #7, never applied. Cost grew
  linearly with ledger age on every admin dashboard load (and the mobile admin
  home route).
- **Fix applied:** SQL aggregation — `DATE_FORMAT(date,'%Y-%m')` GROUP BY with
  `SUM(CASE type WHEN 1 …)`/expense sums, bounded by
  `date >= DATE_FORMAT(DATE_SUB(CURDATE(), INTERVAL n-1 MONTH),'%Y-%m-01')`,
  months clamped to ≤24. The `(user_id, date)` composite index now serves a
  range scan; the query returns ≤ n rows regardless of ledger size. Return
  shape unchanged (`{label,income,expense}[]`); mysql2's DECIMAL-as-string
  sums coerced once.
- **Verified:** executed against the live dev DB (empty scope → zeroed window;
  real scope → 6 labels, numeric, finite) · tsc clean · 182/182 tests · build
  succeeds.

### P4 — unbounded list reads — FIXED (hard caps)
- **Fix applied:** new `LIST_HARD_CAP = 500` in `lib/constants.ts` (documented:
  bounds the worst case without changing what a current user sees; real
  pagination stays on the F-04 `pageBounds` pattern). Applied to:
  - `getPatientBills`, `getPatientPrescriptions`, `getPatientConsultations`,
    `getPatientTestBookings` (all desc-ordered → newest 500) —
    `lib/queries/patient.ts`.
  - `getPatientAppointments`: fetch order flipped to newest-first + cap; the
    existing `byAppointmentDateTime` JS re-sort still presents the retained
    window oldest-first, so the cap can never hide the most recent visits.
  - `getFollowUpReminders` (practice-wide call list, previously ascending and
    unbounded — capping ascending would have hidden the NEWEST reminders):
    fetch newest-first with an id tiebreaker, cap, then `reverse()` to restore
    the ascending presentation.
- **Deliberately left unbounded (with reasons):**
  - `getAllTransactionsForExport` — an export is unbounded by definition.
  - `getMedicineInventory` — bounded by the seeded master catalog, not by user
    activity; the shop page search (`q`) narrows it. Flagged for a product
    decision (server-side pagination of the shop) rather than a silent cap
    that would hide parts of the alphabet.
  - Master/config tables (billing types, vendors, tests, clinics, CMS
    sections) — naturally small.
  - `getChatData` — already `.limit(200)`.
- **Verified:** tsc clean · 182/182 tests · all three guard scripts pass ·
  build succeeds.

### P6 — leading-wildcard `LIKE` on PHI tables — DEFERRED (justified)
- The searches are parameterized (no injection) but `%term%` cannot use a
  B-tree index. The right fix is FULLTEXT indexes or a trigram approach — a
  schema change with migration + tuning cost that only pays off at scales this
  deployment (single box, per-practice row counts in the thousands) does not
  reach. Deferred to the roadmap; revisit if search latency becomes measurable.

### 7.2 Verified UX gaps (with evidence)

> **Status update (session 6):** gaps 1 (form accessibility) and 2 (onboarding)
> have been **implemented and verified** — see §5d. Gaps 3–5 remain open.

1. **Form accessibility is the weakest area (WCAG 2.2 AA risk).** Grep across

   (knowledge-based) win here with guided setup checklists. **Fix direction:** a

   schedule → share booking link), dismissible, driven by existing entity counts.

   bulk-save logic, but no list UI exposes multi-select operations (status
   updates, exports are per-row). **Fix direction:** multi-select on the
   appointments and test-bookings tables for status + export + WhatsApp resend.
   > **Status update (session 7):** bulk status updates for test bookings are

## 8. Session 6 — P2 UX implementations (verified)

### §7.2.1 Form accessibility sweep — DONE
